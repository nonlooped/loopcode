# Desktop release workflow comparison

Checked 2026-08-25. This is a primary-source review of six open-source desktop apps with public GitHub release machinery. Qwen Code Desktop and Cline are direct coding-agent peers. Zed and Lapce are nearby developer-tool peers. Jan and Logseq add useful Tauri and Electron comparisons.

The LoopCode findings below use the tagged v0.8.0 workflow as their baseline. The follow-up implementation applies the recommended small version: tag-bound dispatch, changelog-backed draft notes, checksum generation, refusal to overwrite a published release, and no label-based release taxonomy.

All six have a formal GitHub Release process. I also checked GitHub Desktop, but its public repository only exposes release drafting and release-PR preparation, not the final binary publisher. I left it out of the end-to-end table rather than pretending the missing half was public. Its [draft workflow](https://github.com/desktop/desktop/blob/development/.github/workflows/draft-release.yml) is still worth reading for its reviewed release branch and changelog changes.

## Short answer

LoopCode's build pipeline is mostly sound. The part that feels wrong is the product policy around it. Since [`d99cf1f`](https://github.com/nonlooped/loopcode/commit/d99cf1f97931e03c891038ea09404334656b5976), the repository added a reviewed release branch and curated notes, used that process once for [v0.7.0](https://github.com/nonlooped/loopcode/releases/tag/v0.7.0), then removed the curated notes in [PR #69](https://github.com/nonlooped/loopcode/pull/69). The next release relies on label-based GitHub notes even though its only feature PR has no category label. At the same time, the repository started v0.8.0 less than two hours after publishing v0.7.0, despite its own [weekly stable-release policy](https://github.com/nonlooped/loopcode/blob/v0.8.0/CONTRIBUTING.md#releases).

That puts LoopCode between two healthy models. It has the ceremony of a stable app release, but the cadence and notes quality of a nightly build. Pick one. The smaller choice is to keep stable releases, batch them as already documented, and make the workflow stop at a reviewed draft.

The common shape is simple:

1. A human or a version tag chooses an immutable release commit.
2. CI validates the version and source before reading signing secrets.
3. Platform jobs build, test, sign, and upload temporary artifacts.
4. One job with `contents: write` assembles a draft GitHub Release.
5. A human publishes it, or a tightly defined stable/preview rule does.
6. Updater feeds and app stores move only after that gate.

The strongest small-project model here is Qwen Code Desktop. Cline has excellent source and channel validation, but its current desktop release only ships a universal macOS build and its workflow is much more elaborate. Zed is the large-team version, with full tests, compliance checks, asset validation, GitHub App credentials, and SHA-pinned actions.

## LoopCode since `d99cf1f`

The release path changed in three quick steps:

1. [`d99cf1f`](https://github.com/nonlooped/loopcode/commit/d99cf1f97931e03c891038ea09404334656b5976) routed version bumps through release pull requests, taught master CI to tag the merged release commit, added categorized GitHub notes, and required a curated `RELEASE_NOTES.md` summary.
2. [v0.7.0](https://github.com/nonlooped/loopcode/releases/tag/v0.7.0) showed the intended result. Its page has a useful title, summary, highlights, fixes, availability warning, generated PR list, and five platform packages.
3. [PR #69](https://github.com/nonlooped/loopcode/pull/69) deleted the curated note, validator, test, and CI wiring the next day. v0.8.0 kept only GitHub's label-based generated notes and the tag as its title.

The current workflow has real strengths. It validates all embedded versions against the tag, releases only after the merged commit passes `CI / gate`, checks that the previous tag has a published release, builds Linux and Windows separately, gives build jobs read-only repository access, pins actions to commit SHAs, verifies downloaded AppImage tooling by checksum, serializes releases, and makes artifact upload rerunnable. Keep those parts. See the immutable [v0.8.0 release workflow](https://github.com/nonlooped/loopcode/blob/v0.8.0/.github/workflows/release.yml) and [master tagging job](https://github.com/nonlooped/loopcode/blob/v0.8.0/.github/workflows/ci.yml#L126-L160).

Four things are off:

- **Stable cadence contradicts policy.** v0.7.0 was published at 20:41 UTC. [v0.8.0's release PR](https://github.com/nonlooped/loopcode/pull/71) merged and started its release at 22:33 UTC. Fast-moving peers put this frequency into nightly or prerelease channels. LoopCode calls both releases stable.
- **The two change lists disagree.** [`CHANGELOG.md`](https://github.com/nonlooped/loopcode/blob/v0.8.0/CHANGELOG.md) correctly puts PR #70 under Features because `git-cliff` reads the Conventional Commit title. GitHub's release configuration categorizes by labels, but [PR #70](https://github.com/nonlooped/loopcode/pull/70) has none. Replaying GitHub's `generate-notes` API for v0.8.0 produced one section named `Other changes`. The label taxonomy adds work and already failed on its first release without curated notes.
- **Automatic publication removed the useful review gate.** The publish job creates a draft and immediately flips it public. Peer workflows commonly leave stable releases as drafts so a maintainer can check the notes, warnings, artifact set, and updater metadata before users see them.
- **The identity checks stop one step short.** Master CI dispatches the workflow with `--ref master` while passing the tag and SHA as strings. A later master commit could therefore supply the workflow definition for an older tagged release. Dispatching at the tag removes that race. The job named `provenance` checks prior CI and versions, but it does not create build provenance. Call it `preflight`, or add an actual artifact attestation later.

## Recommendation for LoopCode

Do not add a release framework. The existing shell script and workflows already cover versioning and builds.

1. Keep the release PR, version consistency check, tag-after-green-master rule, matrix build, pinned actions, verified external tools, and single write-enabled publish job.
2. Follow the existing stable cadence. Batch user-visible work instead of cutting a stable minor for every merged feature. Add a nightly channel only when someone needs frequent binaries.
3. Delete the label-based release taxonomy and its contributor instructions. Use the existing top `CHANGELOG.md` section as the generated detail, then add a short human summary or warning in the GitHub draft when it matters. Do not restore the old release-note validator and test.
4. Leave stable releases in draft. Publish after checking the title, notes, expected assets, and unsigned-package warning. This is a real gate and costs less than maintaining another notes system.
5. Dispatch the release workflow at the immutable tag instead of `master`, and rename `provenance` to `preflight` until it produces attestations.

Before wider distribution, signing matters more than more release automation. LoopCode currently publishes unsigned Windows and Linux packages, has no updater manifest, and has no artifact attestation or checksum asset. Qwen, Cline, Zed, Jan, and Logseq spend most of their release complexity on signing, notarization, updater safety, and artifact verification. Copy that priority when the audience justifies it, not their workflow size.

## What the release pages look like

Patch releases are short. Qwen uses GitHub's generated list without a separate narrative. Cline writes a handful of user-facing bullets from its committed changelog. Zed publishes a small curated fix list. Jan puts a human migration notice above generated notes when users need to act. Logseq leads with a beta/data-backup warning. None tries to turn every patch release into a product blog post.

The useful pattern is:

- Put one short human section first when there is a migration, known limitation, or safety warning.
- Follow it with generated or changelog-backed changes and a comparison link.
- Let assets speak for themselves through consistent names. Include updater metadata, signatures, and checksums as first-class release assets.

## What is actually worth copying

For a small Tauri app, copy Qwen's shape, not Zed's size:

- Keep a manual release entry point. Default it to unsigned dry run and draft.
- Treat one SemVer and one commit SHA as release inputs. Validate that the commit is on the protected release branch and that the embedded app version matches.
- Give build jobs read-only repository access. Give one aggregate job `contents: write`.
- Build and smoke-test each operating system before the release becomes public.
- Require the Tauri updater key for real publishes. Fail if macOS signing or notarization material is absent. Verify the resulting signatures rather than trusting the build command.
- Generate one updater manifest and one checksum file after every platform artifact is collected.
- Publish a draft first. Promote the stable updater feed only after the release is no longer draft or prerelease.
- Pin external actions to commit SHAs.

Two things are commonly messy even in established repos. Version drift appears when tags and manifests can disagree, as Lapce does not guard against. Distribution drift appears when beta/nightly/stable are booleans scattered through build jobs. Cline and Qwen avoid that by validating the channel once and keeping stable updater promotion in one final job.

The minimum sensible process is therefore smaller than most of these files: validated version and commit, platform build matrix, signing checks, one draft-release job, then stable-feed promotion. Store publishing, release branches, AI-written notes, compliance reports, and multiple prerelease channels can wait until the project actually needs them.
